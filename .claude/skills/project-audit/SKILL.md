# Project Audit — 멀티 관점 프로젝트 분석

## 개요

코드베이스를 4개 독립 레인으로 조사한 뒤 우선순위 행동 계획을 생성하는 분석 스킬.  
수정·설치·서버 실행 없이 **읽기 전용**으로 동작한다.

---

## 0단계: Ruflo MCP 가용성 확인

분석을 시작하기 전에 `.mcp.json`을 읽어 `claude-flow` 서버 설정을 확인한다.

```
.mcp.json → mcpServers.claude-flow 존재 여부 확인
```

- **서버가 설정되어 있고 세션에서 MCP 도구가 활성화된 경우**: `claude_flow_spawn_agent` 등 ruflo MCP 도구로 하위 에이전트를 위임한다.
- **설정은 있지만 MCP 도구가 비활성 상태인 경우**: "ruflo MCP 서버가 설정되어 있으나 이 세션에서 도구가 활성화되지 않았습니다. autoStart가 false로 설정된 경우 수동 시작이 필요합니다. Claude가 직접 분석을 수행합니다."라고 고지한 뒤 직접 분석한다.
- **설정이 없는 경우**: ruflo 없이 직접 분석한다. ruflo를 사용했다고 말하지 않는다.

---

## 1단계: 병렬 조사 — 4개 레인

가능하면 4개 레인을 **동시에** 실행한다. 각 레인은 독립적이며 서로의 결과를 기다리지 않는다.

### 제약 조건 (모든 레인 공통)

- 소스·설정 파일 수정 금지
- 의존성 설치 금지
- 테스트·빌드·개발 서버 실행 금지
- 비밀값(API key, secret, password) 출력·메모리 저장 금지
- 확인한 사실과 추정을 명확히 구분 (`[사실]` / `[추정]`)
- 모든 문제에 파일 경로와 근거를 함께 기재

---

### 레인 A — 기획

**목표**: 프로젝트가 무엇을 하는지, 누가 쓰는지, 주요 흐름이 무엇인지 파악

읽어야 할 파일:
- `README.md` (있으면)
- `backend/main.py` 또는 진입점 파일
- 라우터·페이지 파일 목록 (`backend/*/router.py`, `frontend/src/pages/*.jsx`)
- 모델 정의 (`backend/models.py`)
- 환경변수 예시 (`.env.example`, 비밀값 제외)

정리할 내용:
1. 제품이 하는 일 (한 단락)
2. 핵심 사용자 유형과 권한 구조
3. 주요 사용자 흐름 (로그인 → 승인 → 사용 → ... 단계별)
4. 미구현이거나 stub로 보이는 기능 (`[추정]` 표시)

---

### 레인 B — 개발

**목표**: 기술 스택, 폴더 구조, 실행 방법, 의존성 현황 파악

읽어야 할 파일:
- `backend/requirements.txt`
- `frontend/package.json`
- `backend/config.py`
- `backend/database.py`
- `frontend/src/api/client.js`

정리할 내용:
1. 기술 스택 표 (백엔드 / 프론트엔드 / DB / 인증 / 외부 API)
2. 폴더 구조 트리 (node_modules, .venv 제외)
3. 로컬 실행 절차 (환경변수 설정 → 백엔드 → 프론트엔드)
4. 버전 불일치·deprecated 패키지·누락된 peer dep (`[사실]`/`[추정]` 구분)
5. 개발 환경 설정 시 막힐 수 있는 지점

---

### 레인 C — 테스트

**목표**: 테스트 범위, 실행 방법, 부족한 검증 파악

읽어야 할 파일:
- `backend/tests/conftest.py`
- `backend/tests/test_*.py` 전체
- `frontend/` 내 `*.test.*`, `*.spec.*` 파일 (없으면 없다고 기록)

정리할 내용:
1. 테스트 실행 명령 (`pytest`, `npm test` 등)
2. 모듈별 테스트 커버리지 현황 (있음/없음/부분)
3. 외부 API·DB를 어떻게 격리하는지 (mock, in-memory, 실제 호출)
4. 빠져 있는 중요 테스트 케이스 — 각 항목에 이유와 파일 경로 기재
5. 프론트엔드 테스트 유무

---

### 레인 D — 리뷰·보안

**목표**: 인증·권한 흐름, 민감정보 처리, 유지보수 위험 파악

읽어야 할 파일:
- `backend/auth/router.py`
- `backend/auth/jwt_utils.py`
- `backend/auth/dependencies.py`
- `backend/admin/router.py`
- `backend/favorites/router.py`
- `frontend/src/contexts/AuthContext.jsx`
- `frontend/src/api/client.js`
- `.gitignore`

정리할 내용:
1. 인증 흐름 다이어그램 (텍스트)
2. 권한 검사 누락·우회 가능 경로 (`[사실]`/`[추정]` 구분)
3. JWT 설정 적절성 (알고리즘, 만료, 저장 방식)
4. 민감정보 노출 위험 (로그·응답 본문·에러 메시지)
5. CORS·쿠키 설정 리뷰
6. 하드코딩된 URL·환경값 (비밀값 출력 금지 — 키 이름과 위치만 기재)
7. 유지보수 위험 (deprecated API 사용, 단일 장애 지점 등)

## 2단계: 결과 통합 — 5개 섹션 리포트

4개 레인 조사가 끝나면 아래 형식으로 리포트를 작성한다.

---

### 1. 프로젝트가 하는 일

레인 A 결과를 바탕으로 한 단락 요약.  
"누가, 무엇을, 어떤 흐름으로 사용하는지"를 포함한다.

---

### 2. 역할별 확인 내용

각 레인의 핵심 발견을 표 또는 불릿으로 정리.  
`[사실]` / `[추정]` 레이블을 유지한다.

| 역할 | 주요 발견 | 파일 경로 |
|------|-----------|-----------|
| 기획 | ... | ... |
| 개발 | ... | ... |
| 테스트 | ... | ... |
| 리뷰·보안 | ... | ... |

---

### 3. 가장 먼저 하면 좋은 일 3가지

각 항목:
- **제목**: 한 줄
- **이유**: 방치했을 때 생기는 문제 / 해결했을 때 얻는 이점
- **영향 파일**: 관련 파일 목록
- **난이도 추정**: 낮음 / 보통 / 높음 `[추정]`

---

### 4. 추천 작업의 계획

우선순위 1번 작업을 기준으로:
- **목표**: 완료 기준(observable)
- **변경 예상 파일**: 목록
- **검증 방법**: 어떻게 Pass/Fail을 판단할 것인지
- **선행 조건**: 먼저 해야 할 것 (있으면)

---

### 5. Ruflo 도구 사용 내역 및 미확인 부분

- **실제 사용한 Ruflo 도구**: 도구명과 위임한 작업 (없으면 "없음 — 직접 분석")
- **확인하지 못한 부분**: 이유와 함께 기재 (예: 파일 접근 권한, 환경 실행 불가)
- **추가 조사 시 필요한 것**: 사용자가 제공해야 할 정보

---

## 출력 품질 기준

- 추정과 사실을 섞지 않는다. 확실하지 않으면 `[추정]`을 붙인다.
- 파일 경로 없이 문제를 제기하지 않는다.
- "취약점이 있을 수 있다"처럼 모호하게 끝내지 않는다 — 구체적인 위치와 조건을 적는다.
- 비밀값(실제 key, secret, password 값)은 어디에도 출력하지 않는다. 키 이름과 파일 경로만 기재한다.
- 리포트 마지막에 "구현하지 않았음 — 분석만 수행" 한 줄을 명시한다.
